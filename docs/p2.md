> A2: Briefly describe how you implemented argument parsing. How do you arrange for the elements of argv[] to be in the right order?
> How do you avoid overflowing the stack page?

**Argument Parsing**:

- In `process_execute()`, I made a page sized copy of `file_name` to prevent race conditions with the caller.I also made a temporary copy and use `strtok_r()` with delimiter `" "` to extract the program name alone when invoking `thread_create()`.By doing so the thread name reflects only the executable name.
- The full command line is passed to `start_process()`.
- In `setup_stack()` I allocated temporary memory for the argument vector `argv` and tokenize the command line string word by word using `strtok_r(cmdline, " ", &save_ptr)`,storing each token pointer in `argv[argc++]`.

**Arranging `argv[]` in the right order**:

- I constructed the initial 80x86 user stack frame starting from `PHYS_BASE` downward:
  a. **Argument Strings**: Pushed in reverse order (`argv[argc - 1]` down to `argv[0]`) using `memcpy()`. The resulting virtual stack address of each string is saved back into `argv[i]`.
  b. **Word Alignment**: `%esp` is rounded down to a 4-byte boundary (`*esp = (void *) ((uintptr_t) *esp & ~3)`) for optimal memory access.
  c. **Null Sentinel**: A null pointer sentinel (`argv[argc] = NULL`, 4 bytes) is pushed to mark the end of the argument array as per C standard.
  d. **Pointers to Strings**: The address pointers (`argv[argc - 1]` down to `argv[0]`) are pushed onto the stack. Because `argv[0]` is pushed last, it resides at the lowest address in the array, making `argv[0]`,`argv[1]`, ..., `argv[argc]` contiguous in ascending order of address.
  e. **`argv` Pointer**: The address of `argv[0]`(the current `%esp`) is pushed onto the stack (`char **`).
  f. **`argc`**: The integer count of arguments (`int`) is pushed.
  g. **Fake Return Address**: A fake return address (`(void *) 0`) is pushed to simulate a standard C function call frame.

**Avoiding Stack Overflow**:

- Before writing to the stack, I computed the total byte requirement:
  `total_size = ROUND_UP(sum_of_string_lengths_with_nulls, 4) + (argc + 1) * sizeof(char *) + sizeof(char **) + sizeof(int) + sizeof(void *)`.
  -Ensure `argc` does not exceed the temporary buffer capacity, and verify that `total_size <= PGSIZE`. If `total_size` exceeds the 4 kB stack page, `setup_stack()` fails and returns `false`, preventing stack overflow and aborting process loading cleanly.

#### RATIONALE

> A3: Why does Pintos implement strtok_r() but not strtok()?

`strtok()` maintains internal static state to remember its current position between successive tokenization calls.In a preemptive, multithreaded kernel like Pintos if two threads or interrupt handlers invoke `strtok()` concurrently they will overwrite each other's static state resulting in race conditions and corrupted parsing.
`strtok_r()` is the reentrant and thread safe equivalent.It requires the caller to explicitly pass the address of a context pointer (`save_ptr`). Each thread maintains its own parsing state on its own execution stack preventing concurrency issues without needing locks.

> A4: In Pintos, the kernel separates commands into a executable name and arguments. In Unix-like systems, the shell does this separation. Identify at least two advantages of the Unix approach.

1. **Kernel Simplicity and Security**:
   String parsing is complex and error prone.Also it is a common source of memory corruption vulnerabilities.Handling complex parsing including quotes, escaping, wildcards and environment variables in user space keeps the kernel simple and robust. An error or crash during parsing only terminates the user shell process rather than causing a kernel panic or kernel privilege escalation.
2. **Flexibility and Modularity**:
   Delegating command line parsing to user space allows different user shells to support distinct syntax, pipeline constructs (`|`), redirections (`>`, `<`) and variable substitutions (`$VAR`) without requiring kernel modifications or kernel level support.
3. **Efficiency**:
   The kernel does not need to allocate kernel memory pages to copy and reparse command strings into argument tokens because the shell already parses arguments in user memory and passes pointers directly.

> B2: Describe how file descriptors are associated with open files. Are file descriptors unique within the entire OS or just within a single process?

File descriptors are associated with open files through `struct process_file` which binds an integer `fd` to a `struct file *`. Each process owns an independent list `file_descriptors` in `struct thread`. When `open()` succeeds a `process_file` is allocated and assigned `cur->next_fd++`.

File descriptors are unique **only within a single process**. Each process manages its own independent descriptor table starting at 2 (0 and 1 are reserved for standard input and output). Distinct processes opening the same file receive independent file descriptors with separate seek positions.

#### ALGORITHMS

> B3: Describe your code for reading and writing user data from the kernel.

I use pointer verification before dereferencing:

1. `is_valid_user_ptr(const void *uaddr, size_t size)` validates user memory ranges:
   - Verifies that `uaddr` is not null.
   - Verifies that `uaddr` is below `PHYS_BASE` using `is_user_vaddr()`.
   - If `size == 0` immediately returns `true` since no memory bytes are accessed.
   - Checks that `uaddr + size` does not overflow 32 bit arithmetic.
   - Verifies the final byte is also below `PHYS_BASE`.
   - Iterates page by page from `pg_round_down(start)` to `end`, checking `pagedir_get_page(cur->pagedir, page) != NULL` to ensure every page in the range is mapped in the current process's page directory.
2. `validate_user_ptr(const void *uaddr, size_t size)`:
   - Calls `is_valid_user_ptr()`. If invalid immediately terminates the offending process with `sys_exit(-1)`.
3. `validate_user_str(const char *uaddr)`:
   - Iterates through a null-terminated string byte by byte. Checks that each byte is below `PHYS_BASE` and checks each new page boundary with `pagedir_get_page()` until reaching `\0`.If an invalid address is encountered, it calls `sys_exit(-1)`.
4. In `syscall_handler()`:
   - Stack arguments are validated before reading: `f->esp` is validated for the syscall number then stack arguments are validated based on the specific syscall signature before reading.
   - Buffers for system calls (such as `write` or `read`) are validated across their entire length before the kernel reads from or writes to them.
5. In `page_fault()` (`userprog/exception.c`):
   - Added kernel page fault recovery (`if (!user && f->eax != 0) { f->eip = (void (*) (void)) f->eax; f->eax = -1; return; }`) to support safe assembly based `get_user`/`put_user` dereferences if kernel mode page faults occur.

- for Full page (4,096 bytes):
  - Least is1 call to `pagedir_get_page()`. This occurs when the buffer is page-aligned (offset 0), so all 4,096 bytes fit entirely within a single virtual page.
  - Greatest is 2 calls to `pagedir_get_page()`. This occurs when the buffer is not page-aligned (e.g., offset 1), straddling two adjacent virtual pages.
- for 2 bytes of data:
  - Least is 1 call to `pagedir_get_page()`. This occurs when both bytes reside within the same page (offsets 0 to 4094).
  - Greatest is 2 calls to `pagedir_get_page()`. This occurs when the 2 bytes span across a page boundary (offset 4095 of page N and offset 0 of page N+1).
- Room for improvement:
  - Under page table verification in software 1 inspection per touched page is the theoretical lower bound since Pintos allocates and maps memory at page granularity (4 kB).
  - However in terms of system performance the software inspection approach can be improved by adopting the hardware MMU or page fault handling approach (Method 2). In Method 2 the kernel dereferences user pointers directly after a simple boundary check (`uaddr < PHYS_BASE`).For valid accesses 0 page table inspections are performed in software reducing software page table lookup overhead by 100%.

> B5: Briefly describe your implementation of the "wait" system call
> and how it interacts with process termination.

1. When a parent process calls `wait(child_tid)`, `process_wait()` searches `cur->children` for a `child_status` struct with matching TID.
2. If the child is not found (not a direct child) or if `child->waited` is already true, it returns -1 immediately.
3. The parent sets `child->waited = true` and waits on `sema_down(&child->sema_exit)`.
4. When the child process terminates (via `exit()` or abnormal kernel termination due to an exception), `process_exit()` writes the exit code to `child->exit_status` and signals `sema_up(&child->sema_exit)`.
5. The parent unblocks, reads `child->exit_status`, removes `child` from `cur->children`, decrements `child->ref_cnt`, and returns the exit status.
6. A reference count (`ref_cnt`) ensures `child_status` is freed only after both parent and child finish referencing it preventing memory leaks and use after free bugs.

> B6: Any access to user program memory at a user-specified address
> can fail due to a bad pointer value. Such accesses must cause the
> process to be terminated. System calls are fraught with such
> accesses, e.g. a "write" system call requires reading the system
> call number from the user stack, then each of the call's three
> arguments, then an arbitrary amount of user memory, and any of
> these can fail at any point. This poses a design and
> error-handling problem: how do you best avoid obscuring the primary
> function of code in a morass of error-handling? Furthermore, when
> an error is detected, how do you ensure that all temporarily
> allocated resources (locks, buffers, etc.) are freed? In a few
> paragraphs, describe the strategy or strategies you adopted for
> managing these issues. Give an example.

To avoid obscuring core system call logic in error-handling code, I adopted an upfront validation strategy:

1. All user provided inputs including the system call number on the stack, system call arguments and user memory buffers or strings are validated before executing the system call logic and before allocating any dynamic resources or acquiring synchronization primitives such as the filesystem lock.
2. The validation helper functions (`validate_user_ptr` and `validate_user_str`) immediately terminate the offending process with `sys_exit(-1)` upon detecting any invalid pointer (NULL, pointer above `PHYS_BASE` unmapped page or arithmetic wraparound).Because validation occurs before resources are acquired, there is no need for convoluted cleanup or rollback logic scattered across individual system call handlers.
3. Any process owned resources that outlive a single system call (such as open file descriptors and page directories) are registered in the `thread` structure and unconditionally reclaimed in `process_exit()`.Also when `sys_exit(-1)` is called Pintos automatically cleans up all process state without leaks.

In `SYS_WRITE (fd, buffer, size)`:

1. `validate_user_ptr(f->esp + 4, 3 * sizeof(int))` verifies that the stack contains 3 valid integer arguments.
2. The arguments `fd`, `buffer` and `size` are extracted.
3. If `size > 0`, `validate_user_ptr(buffer, size)` verifies that the entire user buffer resides in mapped user pages.
4. If any pointer is invalid `sys_exit(-1)` terminates the process immediately. No filesystem locks have been acquired so no orphaned locks or memory leaks can occur.
5. Only once all checks succeed does the handler write to the console or acquire the filesystem lock to write to a file.

#### SYNCHRONIZATION

> B7: The "exec" system call returns -1 if loading the new executable
> fails, so it cannot return before the new executable has completed
> loading. How does your code ensure this? How is the load
> success/failure status passed back to the thread that calls "exec"?

1. When `exec` calls `process_execute()`, the parent allocates a shared `struct child_status` with `sema_load` initialized to 0 and `load_success` set to false.
2. The parent packages this along with the command line in `struct process_start_arg` and calls `thread_create(..., start_process, arg)`.
3. The parent immediately invokes `sema_down(&child->sema_load)`, blocking until the child finishes ELF loading.
4. In `start_process()`, the child executes `load()`. Upon completion (success or failure) the child writes the result to `child->load_success` and signals `sema_up(&child->sema_load)`.
5. The parent thread wakes up. If `child->load_success` is true, `process_execute()` returns the child's `tid`. If false, the parent removes the child from `cur->children`, decrements `child->ref_cnt`, and returns `TID_ERROR` (-1), which `exec` returns to the caller.

> B8: Consider parent process P with child process C. How do you
> ensure proper synchronization and avoid race conditions when P
> calls wait(C) before C exits? After C exits? How do you ensure
> that all resources are freed in each case? How about when P
> terminates without waiting, before C exits? After C exits? Are
> there any special cases?

Proper synchronization and safe resource deallocation are managed using the shared `struct child_status` with a binary semaphore (`sema_exit`), a lock (`lock`) and a reference count (`ref_cnt`, initialized to 2):

1. **P calls `wait(C)` before C exits:**
   - P locates C in `cur->children`, verifies `!C->waited`, marks `C->waited = true`, and invokes `sema_down(&C->sema_exit)`.
   - P blocks because `sema_exit` starts at 0.
   - When C finishes running and calls `process_exit()`, C records its `exit_status` in `C->exit_status`, calls `sema_up(&C->sema_exit)`, and decrements `C->ref_cnt` (from 2 to 1).
   - Signaling unblocks P. P retrieves `C->exit_status`, removes C from `cur->children`, decrements `C->ref_cnt` (from 1 to 0), and frees `struct child_status`.
2. **P calls `wait(C)` after C exits:**
   - C has already terminated, stored its exit code, signaled `sema_up(&C->sema_exit)` and decremented `ref_cnt` to 1.
   - When P later calls `wait(C)`, `sema_down(&C->sema_exit)` does not sleep because the semaphore count is 1.
   - P immediately retrieves `C->exit_status`, decrements `C->ref_cnt` from 1 to 0 and frees `struct child_status`.
3. **P terminates without waiting, before C exits:**
   - When P exits, its `process_exit()` iterates over `cur->children`. For each child P decrements `ref_cnt` from 2 to 1 and removes it.
   - When C subsequently terminates C's `process_exit()` decrements `ref_cnt` from 1 to 0 and frees `struct child_status`.
4. **P terminates without waiting, after C exits:**
   - C terminated first, leaving `ref_cnt` at 1.
   - When P terminates, P's `process_exit()` iterates over `cur->children`, decrements `ref_cnt` from 1 to 0 and frees `struct child_status`.
5. **Special Cases:**
   - **Waiting twice on C:** P checks `child->waited`. If true, `process_wait()` immediately returns -1 without blocking or double-freeing.
   - **Waiting on a non-child:** P searches only `cur->children`. If the TID is not found, `process_wait()` returns -1 immediately.
   - **Abnormal child termination:** If C is terminated due to an exception (segfault/bad pointer) the kernel sets `exit_status = -1`. `process_exit()` still runs, notifying P of exit code -1 via `sema_exit`.

#### RATIONALE

> B9: Why did you choose to implement access to user memory from the
> kernel in the way that you did?

I chose upfront pointer verification using `pagedir_get_page()` and `is_user_vaddr()` because:

1. It ensures the kernel never dereferences an invalid or malicious pointer avoiding kernel mode exceptions and unpredictable execution paths.
2. Rejecting invalid inputs before acquiring any locks or allocating buffers completely eliminates complex rollback and unwinding logic.If an error is detected the process can simply terminate immediately with status -1 without risking deadlocks or leaked kernel resources.
3. Explicit validation keeps failure points clear and isolated from unexpected kernel faults, making debugging straightforward during development.
4. I also equipped the page fault handler (`page_fault()` in `userprog/exception.c`) to safely recover from kernel page faults (`f->eip = f->eax; f->eax = -1;`) ensuring our kernel is compatible with MMU-based assembly dereferences (`get_user`/`put_user`) if required.

> B10: What advantages or disadvantages can you see to your design
> for file descriptors?

**Advantages:**
1. *Dynamic capacity:* Using a per-process linked list (`file_descriptors`) avoids any fixed arbitrary limit on the number of simultaneously opened files per process (bounded only by kernel heap memory).
2. *Memory efficiency:* Only uses memory proportional to currently open files; processes with few or no open files do not waste memory on a large static descriptor array.
3. *Per-process isolation:* Each thread maintains its own descriptor list and sequential ID numbering (`next_fd`), preventing descriptor namespace clashes across processes.

**Disadvantages:**
1. *Lookup latency:* Finding a file descriptor requires an $O(N)$ linear traversal across the linked list rather than an $O(1)$ array index dereference.
2. *Heap fragmentation and allocation overhead:* Each `open` call invokes `malloc()` and each `close` invokes `free()` introducing heap management overhead compared to a fixed array table.

> B11: The default tid_t to pid_t mapping is the identity mapping.
> If you changed it, what advantages are there to your approach?

I retained the default identity mapping where `pid_t` is identical to `tid_t`.

**Advantages of this approach:**
1. *Design simplicity:* In Pintos Project 2 each user process corresponds to exactly one kernel thread. An identity mapping avoids the need for an additional lookup table or PID translation layer in the kernel.
2. *Zero translation overhead:* Thread creation and process management share the exact same IDs, allowing direct use of `tid` for scheduling, list identification, and system call returns.
3. *Sufficient for single-threaded user programs:* Until multi threaded user processes (where multiple threads share one process space and PID) are supported, an identity mapping is optimal and avoids unnecessary complexity.
